
when we create images for front-end, we can minify the size of our code via turning them into static files and we do this by `npm run build` which is a react command to create static files out of our react code, by doing this we can reduce a 500 MB image size to 26 MB and it does it by minifying, uglifying and hardcoding packages into the codes.

so when uploading this on server, since it's lighter it can be served faster to users, therefore this minification has performance benefits. (using servers with better hardware gives us also better speed and user experience but if you have issues and lag working with your server GUI, it's because of your internet connection and the distance between the location of the server and your machine)

we have a web server called nginx, which is like node.js, both of them run our application on the server, for starting our frontend application on the server we use nginx because on the server we have minified frontend files and nginx works better with static files than node.js.

so why we call nginx a web server? we have 2 types of servers, physical and software.
physical are those servers you purchase to deploy your files on it but when you deploy it on that server, how you are going to server them to user, the software web servers like node.js and nginx find those files and run it.

so we should have 2 `Dockerfile`s for our frontend project: one for development and one for production.

in the development we haven't turned our files into static and we use `node.js` and in production we have to test our static files and their new web server which is nginx.

so you may ask why we don't just keep the production `Dockerfile` and just test our application in that? because if we have these two, we can see where the problem is rising, we can understand if the problems belongs to node.js and packages or it belongs to minification and problem with nginx, so it's better to have both `Dockerfile`s and when we added a new feature to our code or it's time to check our app in server-like environment, we have to build both development and production `Dockerfile` images and run both of them.

for backend we have only one Dockerfile since we don't turn them into static files. (they can't turn into static files due to technical reasons)

subsequently we have 2 docker-compose file, one for production and one for development, in the the backend and database share the same service name and `Dockerfile` in both 
Docker-compose files but frontend Docker file in the production should refer to `Dockerfile.prod` which is Dockerfile for production and we remove the test images in the production 
docker-compose file because it slows down our application and we don't need them.
we change the name of the services if their Dockerfile has changed in our docker-compose production file which only the front-end service name changes.

`Dockerfile`:
``` 
FROM node:14.16.0-alpine3.13
RUN addgroup app && adduser -S -G app app
USER app
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 3000
CMD ["npm", "start"]
```

`Dockerfile.prod`:
```
# Build stage
FROM node:14.16.0-alpine3.13 AS build-stage
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# Production stage
FROM nginx:alpine3.23
COPY --from=build-stage /app/build /usr/share/nginx/html
EXPOSE 80
ENTRYPOINT ["nginx", "-g", "daemon off;"]
```

as you can see the production dockerfile differs from the development dockerfile for frontend
in the production Dockerfile we have stages:
A stage is a complete, temporary image used to build something.
each stage starts with a  `FROM`.

so in the `Dockerfile.prod`, first we have a image with `node` and other thing exactly before the second FROM, as soon as it reaches the seconds FROM empty the image layers and create a temporary image from the first FROM image and cache it, we have called the first stage build-stage
, the `AS` next to FROM specifies the name of that stage and this naming feature gives us this ability to use the output of a specific stage in other stages, so each stage start from its FROM till the next FROM, in here in first stage we have build the static files, and we had to use node otherwise how could we install the packages, also we need the nginx, which means we had to discard node, so we have the second stage, we have deleted the user creation and USER instruction since nginx has an issue with it (we had put it next to nginx because we want to login as that user in our container and if we put it in the first stage it would be discarded).

you can see we have used `--from=build-stage` which tells Docker to grab `/app/build` from the fist stage and place it in `/usr/share/nginx/html` which is nginx default root for executing application, also we have expose 80, because nginx runs the application in port 80 and the last command is like `npm start` for nginx.

`docker-compose.prod.yml:`

```
version: "3.8"

services:
  frontend-prod:
    build:
      context: ./frontend
      dockerfile: Dockerfile.prod

    ports:
      - 80:80
        
    restart: unless-stopped

  backend:
    build: ./backend

    ports:
      - 3001:3001
    environment:
     DB_URL: mongodb://db/vidly
    restart: unless-stopped

  db:
   image: mongo:4.0-xenial

   ports:
     - 27017:27017

   volumes:
     - vidly:/data/db
   restart: unless-stopped  

volumes:
  vidly:
```
we have changed the port in the frontend-prod section because no longer the container runs in 300 and nginx runs it in 80 and added the restart properties. 

since we have now 2 `dockerFile` and 2 `docker-compose file`, now each time we're building we have to specify which Dockerfile we mean:

`docker build -f Dockerfile.prod .`

it means in this directory that we're located now, among all of the Dockerfiles pick, `Dockerfile.prod` and `-f` works as a specifier.
`docker-compose -f docker-compose.prod.yml up`

in the docker-compose file, in frontend section, under build we have a `context` and a `dockerfile` properties which context is equal to `.` in `docker build` command
and `dockerfile` is equal to `-f`, context tells docker where to look for a `Dockerfile` and `dockerfile` says which docker file to pick, the reason we don't have these 2 properties in the development docker-compose file is we have `build` property which tells the docker where to find the Dockerfile and since there is only one Dockerfile, we don't need any extra property.

in the `docker run` command always the options comes before the image name like:
`docker run -v ... -d -p ... react-app:1` and if you place the extensions after the image name, the command won't work.

in the `docker-compose up`, the only option that must come before `up` is `-f` and other options should come after the `up`.

`docker-compose -f ... up -d` 

and please each time you add a new feature or it's time to test the code in server-like environment 
or testing your docker images, first build them then run them so use:

`docker-compose -f ... up -d --build`

and first check the development docker images and then production.

we can only have one CMD command in our Dockerfile and if we more than one CMD, the last one will be executed, we use this CMD command for executing the application for other commands we use RUN instruction.
